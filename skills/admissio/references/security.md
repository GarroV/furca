# Гейт безопасности

Сверено 19.10.2026.

> **Решение владельца 19.10.2026:** AITriage остаётся — тонким детерминированным
> ярусом. Формулировка: «тонкий, оставляй, пусть будет». VIGIL его не заменяет и
> не дублирует: AITriage — быстрый гейт на каждый коммит, VIGIL — глубокий аудит
> на вехах поверх, он же потребитель вывода сканера (`vigil ingest`).

Это **прогон инструментов, а не юнит-тесты**: правило «тесты ради тестов не
пишем» он не нарушает. Тест под каждый класс уязвимости — это набор, который
переписывают при каждой правке; детерминированный скан ловит тот же класс один
раз настроенным гейтом. Безопасность попадает в блокирующий набор по той же
причине, что и типы: ошибка здесь **молчит и стоит дорого** — утёкший ключ,
необойдённая авторизация, инъекция не краснеют сами, их не видно с первого
запуска.

Два уровня, не путать:

- **Гейт на каждый коммит / в CI — AITriage.** Детерминированный, дешёвый,
  воспроизводимый. Его место — рядом с линтом в наборе `admissio`.
- **Глубокий аудит на вехах — VIGIL.** Разведка, аналитики по ролям,
  доказательство каждой находки. Не гоняется на каждый коммит (дорого и не нужно):
  перед релизом, после крупной фичи, по запросу. Сырой скан вердиктом не является
  — см. скилл `aitriage` и `vigil-audit`.

## Обязательный набор

| Роль | Команда | Чем / почему |
|---|---|---|
| Секреты | `gitleaks detect --redact` (и в pre-commit, и в CI) | ключ в коде или в истории — самый дешёвый для атакующего и самый дорогой для нас класс; ловится до пуша |
| Детерминированный скан | `aitriage scan . --baseline` | semgrep + gitleaks под одним вердиктом; `--baseline` = «нет находок сверх принятого списка». Установка и триггеры — скилл `aitriage` |

`--baseline` опирается на `.aitriage-baseline.json` + таблицу обоснований в
`docs/security-baseline.md` проекта: **подавление без письменной причины
запрещено** — иначе через месяц скан перестают читать. Шаблон —
`templates/security-baseline.md` (если его нет, взять из FURCA).

## Ситуативные проверки

Опция ставится только когда выполнено её условие.

| Проверка | Включать когда | Команда | НЕ включать когда |
|---|---|---|---|
| SCA зависимостей | есть сторонние пакеты | `osv-scanner -r .` или `npm audit`/`pip-audit` в CI | кода без зависимостей нет, но тогда и проекта нет |
| Скан IaC и образов | есть Terraform, Dockerfile, K8s-манифесты, Helm | `trivy config .` + `trivy image <tag>` | инфраструктура не описана в репозитории |
| Укрепление CI-воркфлоу | проект собирается в GitHub Actions / GitLab CI | `zizmor .github/workflows` (или ручной чек: actions пиннятся по SHA, нет `pull_request_target` с checkout PR-кода, нет `${{ github.event.* }}` в `run:`, `permissions:` сужены) | CI нет |
| Confused-deps / проверка имён пакетов | есть внутренние (приватные) пакеты | пиннинг реестра в `.npmrc`/`pip.conf`, запрет резолва внутреннего имени из публичного реестра | все зависимости публичные |

AI-слой (вызовы модели, агенты, тулзы, MCP, RAG) детерминированным сканом не
ловится — там гейтом служит глубокий аудит VIGIL (роль `haruspex`): инъекция
промпта, вывод модели в sink без проверки, избыточные полномочия агента,
отравление MCP-тулзов. Для продукта с AI-слоем VIGIL на вехе обязателен.

## Проверка, что гейт настоящий

Скан, который не падает на подставленной дыре, — не гейт. Сделать это **командой
проекта** (`make porcha` или аналог), а не памятью человека:

- во временную копию файла положить фейковый секрет (`AWS_SECRET_ACCESS_KEY=...`)
  и строку с инъекцией → прогон обязан дать `AUDIT FAILED` с внятной причиной;
- убедиться, что подстановка применилась (если `sed` молча ничего не заменил,
  «негативный прогон» ложно зелёный — проверено на VIGIL);
- убрать подставленное → прогон снова чистый.
